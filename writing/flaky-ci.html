Fixing a Flaky CI Suite

A red CI that everyone has learnt to ignore is worse than having no CI at all. This is how I got one back to meaning something, on a side project with a 250-test suite, and what it taught me about flaky tests in general.

The Setup

appdoivo is a mobile web app I built for a real event of about 50 people. Its suite has two halves: API and logic tests, and a real-browser UI suite that drives the app with Playwright's WebKit engine (the same engine as iOS Safari) on iPhone SE, 13 and Pro Max screen sizes. A pre-commit hook and GitHub Actions run the whole suite, and a red check means a branch does not merge.

Symptom: Half the UI Suite Failing, Every Run

One day, roughly half of the UI tests started failing on CI, on main too. Locally, everything passed. The failures were not even consistent: a different test dropped out of nearly every run, and each one passed when run alone. For a whole day, nobody read past the red cross, which is exactly how a CI stops protecting anything.

Cause: Two Browsers Starving a Two-Core Runner

Node's test runner runs test files in parallel by default. On a developer machine that is fine. On a two-core GitHub runner, it meant the API suite and the WebKit UI suite fought over the same CPU, and the browser was starved badly enough that the login step timed out even with a generous 25-second allowance.

The first fix pinned CI to one test file at a time and kept local runs parallel, on the reasonable-sounding argument that a laptop has cores to spare and parallel would take half as long.

Measure, Don't Assume

That argument did not survive a measurement. With the suite at 206 tests: 116 seconds serial against 120 seconds parallel, on a developer machine with other work running. Two browser matrices contending for the same cores cost more than they saved, and the parallel runs were the ones producing intermittent failures.

So serial became the rule everywhere, through a small wrapper script behind npm test, so that CI and every laptop run the suite the same way. Serial was not the careful-but-slow option. It was simply the faster one, and the honest one.

The Rest of the Flakes: The Test Was Wrong, Not the App

Fixing the load exposed a handful of intermittent failures that had been hiding in the noise. Every one of them turned out to be a timing assumption inside the test:

  • Measuring too early. A test opened a row and measured an element's width in the same tick. On a loaded run that caught the layout at zero. It now waits for the element to be laid out.
  • Clicking a node that no longer exists. A list re-rendered while it loaded, so a one-shot click could land on an element that had just been replaced, and the click was silently lost. A Playwright locator, which re-resolves on every attempt, fixed it.
  • A timeout that wasn't. One wait passed its options where Playwright expects a function argument, so it had quietly been using the default 30 seconds instead of the suite's own value.
  • Reading a colour mid-animation. Months later, the first CI run on the public repo failed one test out of 258: on a slower runner, a button label read rgba(231, 231, 231, 0.976) instead of white, because the light/dark fade had not finished. The fix waits for running animations to settle before comparing colours.

None of these was fixed with a retry. A retry would have turned each one into a test that passes for the wrong reason.

What I Took From It

  • A flaky test is a bug with a cause. It depends on some timing or resource the test never stated. Find it and make the test state it.
  • Measure before choosing a trade-off. "Parallel is faster" is usually true and was false here.
  • Protect the meaning of red. A pipeline people have learnt to ignore costs more than it saves. Getting it back to trustworthy was worth more than any single feature that week.
  • Write the reason down next to the fix. The wrapper script carries the measurement in a comment, so nobody has to rediscover why the suite runs serially.
